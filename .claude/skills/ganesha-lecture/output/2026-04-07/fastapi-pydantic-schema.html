ガネーシャ×ナツキの対話で学ぶ、FastAPIのデータ定義

スキーマとは「データの形を定義する契約書」や。入力（リクエスト）と出力（レスポンス）でデータの形が違うから、場面ごとにスキーマを分けるんや。「何を受け取って、何を返すか」をハッキリさせることで、APIは安全で分かりやすくなる。

スキーマ＝データの契約書

Pydantic BaseModelで作る設計図

まずな、スキーマっちゅうのは、PythonではPydanticっていうライブラリのBaseModelを使って作るんや

「Pydantic（パイダンティック）」とは？

データの形をチェックしてくれる検査係のこと。

窓口で「この欄が空欄ですよ」「ここは数字を書いてください」と教えてくれる人みたいなもんや。この解説では「データチェック係」と呼ぶで。

つまり、スキーマを定義すると自動でデータをチェックしてくれるってことですか？

その通りや！実際のコードを見てみ👇

このコードがやること

「タグの登録・更新用の書類フォーマット」を定義しています。titleという項目が必須で、1文字以上の文字列であることをルール化しています。

from pydantic import BaseModel, Field
class InsertAndUpdateTagSchema ( BaseModel ):
title : str = Field(
... ,
description="タグのタイトルを入力してください。",
example="和食",
min_length=1
)

InsertAndUpdateTagSchema — 「タグ登録・更新用の書類」という名前の設計図。申込用紙のタイトル

(BaseModel) — Pydanticの設計図ひな型を使う宣言。「この用紙は公式フォーマットに従います」

title: str — 「title」という項目は文字列（テキスト）。「名前」欄は文字で書いてね

str — 文字列型。数字じゃなくてテキストを受け取る

Field(...) — この項目は必須（省略不可）。「※必ず記入してください」の注意書き

min_length=1 — 最低1文字は必要。空欄はダメですよ

おお！Field(...)の...が「必須」って意味なんですね。申込用紙の「※必須」と同じだと思えば簡単です

② 応答: { tag_id: 1, title: "和食" }

その通りや！整理するとこうなる👇

方向 場面 必要なデータ 使うスキーマ
クライアント → サーバー タグを登録・更新 titleだけ InsertAndUpdateTagSchema
サーバー → クライアント タグ情報を返す title + tag_id TagSchema
サーバー → クライアント 処理結果を通知 messageだけ ResponseSchema

入力と出力でデータの形が違うから、スキーマも分けなアカンのや。場面ごとに最適な形を用意する。これがスキーマを分ける理由やで

継承でスキーマを賢く作る

共通部分はコピーして使い回す

ほな、実際のスキーマ3つを全部見てみよか👇

このコードがやること

3つのスキーマ（書類フォーマット）を定義しています。②は①を継承（コピー）して、tag_idを追加しているのがポイントです。

# ① リクエスト用（登録・更新のときに受け取るデータ）
class InsertAndUpdateTagSchema(BaseModel):
title: str = Field(..., min_length=1)
# ② レスポンス用（タグ情報を返すときのデータ）
class TagSchema(InsertAndUpdateTagSchema): # ← ①を継承！
tag_id: int = Field(...)
# ③ メッセージ用（処理結果を返すときのデータ）
class ResponseSchema(BaseModel):
message: str = Field(...)
継承の関係図
BaseModel（ひな型）

Pydanticの基本機能

InsertAndUpdateTagSchema

title のみ

継承
TagSchema

title（親から引き継ぎ）

+ tag_id（追加）

ResponseSchema

message のみ

継承ってなんですか？TagSchema(InsertAndUpdateTagSchema)の部分ですよね？

ええ質問や。継承ってのはな、親の設計図をまるっとコピーして、さらに項目を追加する仕組みのことや

「継承」とは？

親の書類フォーマットをそのまま引き継いで、新しい項目を追加すること。

たとえば、転入届（名前・住所）をコピーして、受理番号欄を追加したら受理証明書になる。ゼロから作り直さなくていいから楽やし、titleの定義を2回書かなくて済む。

継承なしの場合
  • titleの定義を2回書く
  • 修正するとき2か所直す
  • 書き間違えるリスクあり
継承ありの場合
  • titleの定義は1回だけ
  • 修正するとき1か所だけ
  • 常に同じ定義が使われる

あ、つまりTagSchemaはInsertAndUpdateTagSchemaのtitleをそのまま受け継いで、tag_idだけ追加してるんですね！

Don't Repeat Yourself…同じこと繰り返すなって意味や。ワシも釈迦に「同じギャグ繰り返すな」って言われたことあるわ

エンドポイントでの使い分け

APIの窓口ごとにスキーマを使い分ける

「エンドポイント」とは？

APIの窓口のこと。銀行なら「口座開設窓口」「振込窓口」「解約窓口」みたいに、目的ごとに別々の窓口（URL）がある。それがエンドポイントや。

このコードがやること

タグのCRUD（登録・取得・更新・削除）の4つの窓口を定義しています。それぞれ受け取るデータと返すデータの形が違います。

# 【POST】タグを新規登録する窓口
@router.post("/tags", response_model=TagSchema)
async def create_tag(tag: InsertAndUpdateTagSchema): ...
# 【GET】タグ一覧を取得する窓口
@router.get("/tags", response_model=list[TagSchema])
async def get_tags(): ...
# 【PUT】タグを更新する窓口
@router.put("/tags/{tag_id}", response_model=ResponseSchema)
async def update_tag(tag_id: int, tag: InsertAndUpdateTagSchema): ...
# 【DELETE】タグを削除する窓口
@router.delete("/tags/{tag_id}", response_model=ResponseSchema)
async def delete_tag(tag_id: int): ...

各エンドポイントで受け取るスキーマと返すスキーマをまとめるとこうや👇

HTTPメソッド 操作 受け取る（リクエスト） 返す（レスポンス）
POST /tags 登録 InsertAndUpdateTagSchema
(title)		 TagSchema
(title + tag_id)
GET /tags 一覧取得 なし list[TagSchema]
(title + tag_id のリスト)
PUT /tags/{id} 更新 InsertAndUpdateTagSchema
(title)		 ResponseSchema
(message)
DELETE /tags/{id} 削除 なし ResponseSchema
(message)

間違えやすいポイント

よくある3つの間違いを防ごう

ほんでな、ここからが大事やで。よくある間違いを3つ教えたるわ

間違い① 全部同じスキーマにしちゃう
# ❌ ダメな例：全部入りスキーマ
class TagSchema(BaseModel):
tag_id: int # ← 登録時にクライアントが知るわけない！
title: str
message: str # ← タグ情報を返すときにmessageいらん！
問題 なぜ困るか
登録時にtag_idが必須になるクライアントはIDを知らないのに求められる
一覧取得でmessageが出るタグ情報なのに余計な項目が混ざる
バリデーションが正しく機能しない場面によって不要な項目までチェックされる

確かに…申込用紙と受理証明書を1枚にまとめたら、どこに何を書けばいいか分からなくなりますね

間違い② response_modelを指定しない

❌ ダメな例

@router.get("/tags")
async def get_tags():
return tags
# ← 何が返ってくるか分からない！

✅ 良い例

@router.get("/tags",
response_model=list[TagSchema])
async def get_tags():
return tags
# ← TagSchemaの形で返ることが保証！

response_modelを書かないと、返すデータの形が保証されません。さらに、FastAPIはresponse_modelを指定すると自動でAPIドキュメント（Swagger UI）にも反映してくれます。

間違い③ 継承の方向を間違える

❌ 逆方向の継承

class InsertAndUpdateTagSchema
(TagSchema):
pass
# tag_idも含まれてしまう！

✅ 正しい方向の継承

class TagSchema
(InsertAndUpdateTagSchema):
tag_id: int = Field(...)
# tag_idを追加するだけ

小さい方（項目が少ない方）を親にして、大きい方が継承するのが正しい方向です。

小さい方を親にして、大きい方が継承するんですね！

バリデーションの自動チェック

スキーマが門番になってくれる

もう一個だけ教えたるわ。スキーマを定義するとな、バリデーション（データの検査）が自動で動くんや

さっきのmin_length=1みたいなやつですか？

送られたデータ titleの値 結果
{"title": "和食"} "和食" ✅ OK!
{"title": ""} "" (空文字) ❌ エラー!
min_length=1に違反
{} titleがない ❌ エラー!
必須項目(...)が未入力
{"title": 123} 数値 ❌ エラー!
str(文字列)じゃない

えっ、すごい…！自分でバリデーションのコード書かなくていいんですか！

そや！FastAPIはリクエストが来た瞬間に、スキーマの定義に合うかチェックして、ダメなら自動で422エラー（バリデーションエラー）を返してくれるんや

バリデーションの流れ

不正なデータは門前払い

クライアントがリクエスト送信
{"title": ""}
🔍 スキーマで検査
min_length=1 を満たしている？
YES → 通過
エンドポイントの処理へ
正常にデータベース操作
NO → 門前払い
422 エラーを自動返却
「titleは1文字以上必要です」

おお！不正なデータがエンドポイントの処理に入る前にブロックされるんですね

そういうことや。スキーマは門番みたいなもんやな。おかしなデータは門前払いや
