# 📋 FastAPIのスキーマ（Pydantic BaseModel）の役割と使い分け

> **結論: スキーマとは「データの形を定義する契約書」や。**
> 入力（リクエスト）と出力（レスポンス）でデータの形が違うから、場面ごとにスキーマを分けるんや。
> 「何を受け取って、何を返すか」をハッキリさせることで、APIは安全で分かりやすくなる。

## 📜 スキーマ＝データの契約書

🐘「まずな、**スキーマ**っちゅうのは、Pythonでは**Pydantic**っていうライブラリの**BaseModel**を使って作るんや」

> 💡 **「Pydantic（パイダンティック）」とは？**
> データの形をチェックしてくれる**検査係**のこと。
> 窓口で「この欄が空欄ですよ」「ここは数字を書いてください」と教えてくれる人みたいなもんや。
> この解説では「**データチェック係**」と呼ぶで。

👩‍💻「つまり、スキーマを定義すると自動でデータをチェックしてくれるってことですか？」

🐘「その通りや！実際のコードを見てみ👇」

```python
from pydantic import BaseModel, Field

class InsertAndUpdateTagSchema(BaseModel):
    title: str = Field(
        ...,
        description="タグのタイトルを入力してください。",
        example="和食",
        min_length=1
    )
```

🐘「このコードがやっとることは、こういうことや👇」

| コードの部分 | 意味 | たとえ |
|------------|------|--------|
| `class InsertAndUpdateTagSchema` | 「タグ登録・更新用の書類」という名前の設計図 | 申込用紙のタイトル |
| `(BaseModel)` | Pydanticの設計図ひな型を使う宣言 | 「この用紙は公式フォーマットに従います」 |
| `title: str` | 「title」という項目は文字列（テキスト） | 「名前」欄は文字で書いてね |
| `Field(...)` | この項目は**必須**（省略不可） | 「※必ず記入してください」の注意書き |
| `min_length=1` | 最低1文字は必要 | 空欄はダメですよ |
| `example="和食"` | 記入例 | 「（例：山田太郎）」みたいなやつ |

👩‍💻笑顔「おお！`Field(...)`の`...`が『必須』って意味なんですね。なんか記号だけだと分かりにくいけど、申込用紙の『※必須』と同じだと思えば簡単です」

🐘得意げ「せやろ？さすガネーシャや！✨ ワシの教え子のザッカーバーグくんもな、Facebook作るとき『データの形を先に決めるのが大事やで』って言うてたわ」

👩‍💻呆れ「…本当ですか？そのエピソード、毎回盛ってません？」

## 🔄 なぜスキーマを分けるのか？

🐘「ほな次や。なんで**スキーマを分ける**必要があるんか、説明したるわ」

👩‍💻疑問「確かに、全部同じスキーマじゃダメなんですか？1つで済むなら楽じゃないですか？」

🐘「ええ質問やな。ほな聞くけど、お前が**タグを新しく登録する**とき、**tag_id**って自分で決めるか？」

👩‍💻「いえ、IDはサーバー側で自動的に振られるものですよね…？」

🐘「そや！！ほな、登録するときの書類に『ID欄』があったらどう思う？」

👩‍💻「え、困ります…。自分じゃ分からないし、適当に書いたら重複しそうだし」

🐘「やろ？つまりな👇」

```
【タグを登録するとき（リクエスト）】

  クライアント ──→ サーバー
  
  送るデータ:
  ┌──────────────┐
  │ title: "和食" │  ← titleだけでOK！
  └──────────────┘
  
  ❌ tag_idは送らない（サーバーが自動で決める）


【タグ一覧を取得するとき（レスポンス）】

  サーバー ──→ クライアント
  
  返すデータ:
  ┌──────────────────┐
  │ tag_id: 1        │  ← IDがないとどのタグか区別できない！
  │ title: "和食"     │
  ├──────────────────┤
  │ tag_id: 2        │
  │ title: "洋食"     │
  └──────────────────┘
```

👩‍💻感動「あー！なるほど！**データの流れる方向**によって必要な項目が違うんですね！」

🐘「その通りや！整理するとこうなる👇」

| 方向 | 場面 | 必要なデータ | 使うスキーマ |
|------|------|------------|------------|
| クライアント → サーバー | タグを登録・更新 | titleだけ | `InsertAndUpdateTagSchema` |
| サーバー → クライアント | タグ情報を返す | title + tag_id | `TagSchema` |
| サーバー → クライアント | 処理結果を通知 | messageだけ | `ResponseSchema` |

🐘「**入力と出力でデータの形が違う**から、スキーマも分けなアカンのや」

👩‍💻「1つのスキーマに全部詰め込むと、『登録時にtag_idどうすんの？』って問題が起きちゃうんですね」

🐘得意げ「そういうことや。**場面ごとに最適な形**を用意する。これがスキーマを分ける理由やで」

## 👪 継承でスキーマを賢く作る

🐘「ほな、実際のスキーマ3つを全部見てみよか。まずはこれや👇」

```python
# ① リクエスト用（登録・更新のときに受け取るデータ）
class InsertAndUpdateTagSchema(BaseModel):
    title: str = Field(
        ...,
        description="タグのタイトルを入力してください。",
        example="和食",
        min_length=1
    )

# ② レスポンス用（タグ情報を返すときのデータ）
class TagSchema(InsertAndUpdateTagSchema):  # ← ①を継承！
    tag_id: int = Field(
        ...,
        description="タグを一意に識別するID番号",
        example=123
    )

# ③ メッセージ用（処理結果を返すときのデータ）
class ResponseSchema(BaseModel):
    message: str = Field(
        ...,
        description="API操作の結果を説明するメッセージ",
        example="タグの更新に成功しました。"
    )
```

🐘「このコードがやっとることを図にするとな👇」

```
               BaseModel（ひな型）
              ┌─────────────┐
              │ Pydanticの   │
              │ 基本機能     │
              └──────┬──────┘
                     │
         ┌───────────┼───────────┐
         │           │           │
         ▼           │           ▼
  ┌──────────────┐   │   ┌──────────────┐
  │ InsertAnd    │   │   │ Response     │
  │ UpdateTag    │   │   │ Schema       │
  │ Schema       │   │   │              │
  │              │   │   │ - message    │
  │ - title      │   │   └──────────────┘
  └──────┬───────┘   │
         │ 継承       │
         ▼           │
  ┌──────────────┐   │
  │ TagSchema    │   │
  │              │   │
  │ - title      │ ← titleは親から引き継ぎ！
  │ - tag_id     │ ← tag_idだけ追加！
  └──────────────┘
```

👩‍💻疑問「**継承**ってなんですか？`TagSchema(InsertAndUpdateTagSchema)`の部分ですよね？」

🐘「ええ質問や。**継承**ってのはな、**親の設計図をまるっとコピーして、さらに項目を追加する**仕組みのことや」

> 💡 **「継承」とは？**
> 親の書類フォーマットを**そのまま引き継いで**、新しい項目を追加すること。
> たとえば、転入届（名前・住所）をコピーして、受理番号欄を追加したら受理証明書になる。
> ゼロから作り直さなくていいから**楽**やし、**titleの定義を2回書かなくて済む**。

| 継承なしの場合 | 継承ありの場合 |
|--------------|-------------|
| titleの定義を2回書く | titleの定義は1回だけ |
| 修正するとき2か所直す | 修正するとき1か所だけ |
| 書き間違えるリスクあり | 常に同じ定義が使われる |

👩‍💻笑顔「あ、つまり`TagSchema`は`InsertAndUpdateTagSchema`の**title**をそのまま受け継いで、**tag_id**だけ追加してるんですね！」

🐘「そういうことや！コードの重複を減らせるし、titleの定義を変えたくなったら**親だけ直せば子にも反映される**んや」

👩‍💻「DRY原則ってやつですね…あ、DRYって…」

🐘ボケをかます「Don't Repeat Yourself…**同じこと繰り返すな**って意味や。ワシも釈迦に『同じギャグ繰り返すな』って言われたことあるわ」

👩‍💻呆れ「…ガネーシャさんは繰り返しがちですもんね」

## 🛣️ エンドポイントでの使い分け

🐘「ほな、実際にAPIの**エンドポイント**（窓口）でどう使い分けるか見てみよか」

> 💡 **「エンドポイント」とは？**
> APIの**窓口**のこと。銀行なら「口座開設窓口」「振込窓口」「解約窓口」みたいに、
> 目的ごとに別々の窓口（URL）がある。それがエンドポイントや。

```python
# 【POST】タグを新規登録する窓口
@router.post("/tags", response_model=TagSchema)
async def create_tag(tag: InsertAndUpdateTagSchema):
    # tag.title を受け取って、DBに保存
    # サーバーが tag_id を自動採番
    # TagSchema（title + tag_id）で返す
    ...

# 【GET】タグ一覧を取得する窓口
@router.get("/tags", response_model=list[TagSchema])
async def get_tags():
    # DBから全タグを取得
    # TagSchema（title + tag_id）のリストで返す
    ...

# 【PUT】タグを更新する窓口
@router.put("/tags/{tag_id}", response_model=ResponseSchema)
async def update_tag(tag_id: int, tag: InsertAndUpdateTagSchema):
    # tag.title を受け取って、指定IDのタグを更新
    # ResponseSchema（message）で結果を返す
    ...

# 【DELETE】タグを削除する窓口
@router.delete("/tags/{tag_id}", response_model=ResponseSchema)
async def delete_tag(tag_id: int):
    # 指定IDのタグを削除
    # ResponseSchema（message）で結果を返す
    ...
```

🐘「各エンドポイントで**受け取るスキーマ**と**返すスキーマ**をまとめるとこうや👇」

| HTTPメソッド | 操作 | 受け取る（リクエスト） | 返す（レスポンス） |
|------------|------|---------------------|-------------------|
| `POST /tags` | 登録 | `InsertAndUpdateTagSchema`（title） | `TagSchema`（title + tag_id） |
| `GET /tags` | 一覧取得 | なし | `list[TagSchema]`（title + tag_id のリスト） |
| `PUT /tags/{id}` | 更新 | `InsertAndUpdateTagSchema`（title） | `ResponseSchema`（message） |
| `DELETE /tags/{id}` | 削除 | なし | `ResponseSchema`（message） |

👩‍💻感動「おお！こうやって表にするとスッキリ分かりますね！」

🐘「ポイントはな、**データの流れる方向と場面**で使い分けとるっちゅうことや」

```
  【データの流れ全体像】

  クライアント（ブラウザ/アプリ）          サーバー（FastAPI）
  ┌─────────────────┐              ┌─────────────────┐
  │                 │   POST/PUT   │                 │
  │  title:"和食"   │ ──────────→  │  titleを受け取り  │
  │                 │  リクエスト    │  tag_idを自動採番 │
  │ InsertAndUpdate │              │                 │
  │ TagSchema       │              │                 │
  │                 │   GET応答    │                 │
  │  tag_id + title │ ←──────────  │  DBから取得して   │
  │  を受け取る      │  レスポンス   │  返す            │
  │ TagSchema       │              │                 │
  │                 │  DELETE応答   │                 │
  │  messageを      │ ←──────────  │  削除して結果を   │
  │  受け取る        │  レスポンス   │  メッセージで返す │
  │ ResponseSchema  │              │                 │
  └─────────────────┘              └─────────────────┘
```

👩‍💻「なるほど…。POSTで登録したときは`TagSchema`で返すんですね。登録した結果を、IDつきで教えてくれるってことか」

🐘「そや！『ちゃんと登録できたで、IDは123番やで』って返してあげるわけや。クライアント側はそのIDを使って後から更新や削除ができるようになるんや」

## ⚠️ 間違えやすいポイント

🐘「ほんでな、ここからが大事やで。よくある**間違い**を3つ教えたるわ」

### 間違い①：全部同じスキーマにしちゃう

👩‍💻疑問「さっきも聞きましたけど、改めて…1つのスキーマじゃダメなんですか？」

🐘「あかん。見てみ👇」

```python
# ❌ ダメな例：全部入りスキーマ
class TagSchema(BaseModel):
    tag_id: int       # ← 登録時にクライアントが知るわけない！
    title: str
    message: str      # ← タグ情報を返すときにmessageいらん！
```

🐘「これやとな、**登録時にtag_idを送れって言われる**し、**一覧取得でmessageが混ざる**し、めちゃくちゃになるんや」

| 問題 | なぜ困るか |
|------|----------|
| 登録時にtag_idが必須になる | クライアントはIDを知らないのに求められる |
| 一覧取得でmessageが出る | タグ情報なのに余計な項目が混ざる |
| バリデーションが正しく機能しない | 場面によって不要な項目までチェックされる |

👩‍💻「確かに…申込用紙と受理証明書を1枚にまとめたら、どこに何を書けばいいか分からなくなりますね」

### 間違い②：response_modelを指定しない

🐘「次はこれや👇」

```python
# ❌ ダメな例：response_modelなし
@router.get("/tags")
async def get_tags():
    return tags  # ← 何が返ってくるか分からない！

# ✅ 良い例：response_modelあり
@router.get("/tags", response_model=list[TagSchema])
async def get_tags():
    return tags  # ← TagSchemaの形で返ることが保証される！
```

🐘「`response_model`を書かへんと、**返すデータの形が保証されへん**のや。これはな、窓口に『お渡しする書類のサンプル』が貼ってないようなもんや」

👩‍💻「お客さん（フロントエンド）が『何が返ってくるか分からない』って困りますね」

🐘「しかもな、FastAPIは`response_model`を指定すると**自動でAPIドキュメント（Swagger UI）にも反映**してくれるんや。つまり窓口の案内板を自動で作ってくれる」

### 間違い③：継承の方向を間違える

🐘「最後はこれ。地味やけど大事やで👇」

```python
# ❌ ダメな例：逆方向の継承
class InsertAndUpdateTagSchema(TagSchema):  # TagSchemaを継承
    pass  # tag_idも含まれてしまう！

# ✅ 良い例：正しい方向の継承
class TagSchema(InsertAndUpdateTagSchema):  # InsertAndUpdateTagSchemaを継承
    tag_id: int = Field(...)  # tag_idを追加
```

| 継承の方向 | 結果 |
|-----------|------|
| ❌ リクエスト用 ← レスポンス用 | リクエストにtag_idが混入する |
| ✅ レスポンス用 ← リクエスト用 | レスポンスにtag_idを追加するだけ |

👩‍💻笑顔「**小さい方（項目が少ない方）を親にして、大きい方が継承する**んですね！」

🐘得意げ「さすガネーシャや！✨ …いや、さすナツキや！飲み込み早いな」

👩‍💻呆れ「自分で自分を褒めるのやめてくださいよ…」

## 🎯 バリデーションの自動チェック

🐘「もう一個だけ教えたるわ。スキーマを定義するとな、**バリデーション（データの検査）が自動で動く**んや」

👩‍💻「さっきの`min_length=1`みたいなやつですか？」

🐘「そや！例えばな、こういうリクエストが来たらどうなるか👇」

| 送られたデータ | `title`の値 | 結果 |
|--------------|-------------|------|
| `{"title": "和食"}` | `"和食"` | ✅ OK! |
| `{"title": ""}` | `""` (空文字) | ❌ エラー！`min_length=1`に違反 |
| `{}` | titleがない | ❌ エラー！必須項目(`...`)が未入力 |
| `{"title": 123}` | 数値 | ❌ エラー！`str`（文字列）じゃない |

🐘「こういうチェックを**自分でif文を書かんでも、スキーマが勝手にやってくれる**んや」

👩‍💻感動「えっ、すごい…！自分でバリデーションのコード書かなくていいんですか！」

🐘「そや！FastAPIはリクエストが来た瞬間に、スキーマの定義に合うかチェックして、ダメなら**自動で422エラー（バリデーションエラー）を返してくれる**んや」

```
  【バリデーションの流れ】

  クライアント         FastAPI              エンドポイント
      │                  │                     │
      │ {"title": ""}   │                     │
      │ ───────────────→ │                     │
      │                  │ スキーマで検査 🔍    │
      │                  │ min_length=1に違反！ │
      │  422エラー        │                     │
      │ ←─────────────── │                     │
      │ "titleは1文字    │  ❌ ここまで到達     │
      │  以上必要です"    │    しない！          │
      │                  │                     │
```

👩‍💻「おお！不正なデータがエンドポイントの処理に入る前にブロックされるんですね」

🐘「そういうことや。スキーマは**門番**みたいなもんやな。おかしなデータは門前払いや」

## 📋 まとめ

🐘「ほな、今日の話をまとめるで！」

| スキーマ名 | 役割 | 持ってる項目 | 使う場面 |
|-----------|------|------------|---------|
| `InsertAndUpdateTagSchema` | 入力用の契約書 | `title` のみ | POST（登録）、PUT（更新） |
| `TagSchema` | 出力用の契約書 | `title` + `tag_id` | GET（一覧取得）、POST（登録結果） |
| `ResponseSchema` | 処理結果通知 | `message` のみ | PUT（更新結果）、DELETE（削除結果） |

🐘「覚えといてほしいのは、この3つのポイントや👇」

```
┌───────────────────────────────────────────────────┐
│  🔑 スキーマの3大ポイント                           │
```
