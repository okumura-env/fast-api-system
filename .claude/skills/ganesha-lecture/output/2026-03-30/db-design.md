## 📍 最重要！配車の心臓部 — `date_vehicle`テーブル

> 難しそうな名前ですが、要は**「いつ・どの車を・誰が運転するか」を決めること**。

```
  日付（いつ？）    車両（どの車？）   ドライバー（誰が？）

   3月30日    ×    ダンプ1号車   ×    田中さん
   3月30日    ×    ダンプ2号車   ×    鈴木チーム
   3月31日    ×    ジェットパック1号  ×  佐藤さん
```

🐘「これが `date_vehicle` テーブルの正体や。**日付×車両×ドライバー**の組み合わせを記録しとる」

👩‍💻笑顔「あ、ホテルの予約表って考えたらめっちゃわかりやすい！」

```
 date_vehicle テーブルの排他制約 ⚡

  ┌─────────────────────────────────────┐
  │  user_id（個人ドライバー）          │
  │        ↕ どちらか一方だけ！         │
```

## 🚛 ダンプ配車の流れ — 3層構造を理解せよ！

🐘「さて、ここからがメインディッシュや。**ダンプ配車**の3層構造を教えたる」

👩‍💻「3層構造…？」

🐘「ハンバーガー🍔を想像してみ」

```
 ダンプ配車の3層構造 = ハンバーガー 🍔

  ┌─────────────────────────────────┐
  │  🍞 上のバンズ = date_vehicle   │  ← 「いつ・どの車・誰」
  ├─────────────────────────────────┤
  │  🥩 パティ = dump_schedules    │  ← 「何の予定か」
  ├─────────────────────────────────┤
  │  🧀 具材 = dump_orders         │  ← 「具体的な内容」
  │        or dump_other_schedules │
  └─────────────────────────────────┘
```

🐘「まず `date_vehicle`（バンズ）で**いつ・どの車・誰が**を決める」

🐘「次に `dump_schedules`（パティ）で**どんな種類の予定か**を決める。ここには `type` っちゅうカラムがあってな👇」

| type の値 | 意味 | 例 |
|---|---|---|
| `order` | 受注による配車 | 石炭をA地点に3往復運ぶ |
| `other` | その他の予定 | 車検、点検、休暇 |

👩‍💻「typeがorderなら `dump_orders`、otherなら `dump_other_schedules` に詳細が入るってことですか？」

## 🔄 3つの配車パターン — 同じ構造の繰り返し！

🐘「ほんでな、ここがこのDB設計の**美しいところ**や」

👩‍💻疑問「美しい…？」

🐘「ダンプ、ジェットパック、WP・PKS。この3つは**全部同じパターン**で作られとる！」

```
 3つの配車パターン（全部同じ構造！）

  【ダンプ】
  date_vehicle → dump_schedules → dump_orders
                                → dump_other_schedules

  【ジェットパック】
  date_vehicle → jetpack_schedules → jetpack_orders
                                   → jetpack_other_schedules

  【WP・PKS】
  date_vehicle → wp_pks_schedules → wp_pks_orders → wp_pks_order_tasks
```

| 車両タイプ | スケジュール | 受注詳細 | その他予定 |
|---|---|---|---|
| 🚛 ダンプ | `dump_schedules` | `dump_orders` | `dump_other_schedules` |
| 🚜 ジェットパック | `jetpack_schedules` | `jetpack_orders` | `jetpack_other_schedules` |
| 🏗️ WP・PKS | `wp_pks_schedules` | `wp_pks_orders` | — |

👩‍💻笑顔「あ！本当だ、全部 `date_vehicle` → スケジュール → 受注 の流れになってる！」

🐘得意げ「そや！**パターンが同じ**やから、1つ理解したら残り2つも自動的にわかる。これが**良いDB設計**っちゅうもんや」

👩‍💻「でも、なんで1つのテーブルにまとめないで、車両タイプごとに分けてるんですか？」

🐘「ええ質問やな！**受注の中身が全然違う**からや👇」

| | ダンプ | ジェットパック | WP・PKS |
|---|---|---|---|
| 固有の情報 | 炭種、往復回数、ボイラー番号 | 搬出先（destination） | タスク一覧（多対多） |
| テーブル構造 | カテゴリ×アイテムの2段階 | シンプルに搬出先1つ | タスクとの中間テーブル |

🐘「ダンプは炭種やボイラー番号が必要やし、ジェットパックは搬出先が大事やし、WP・PKSはタスクの組み合わせが大事や。**無理に1つにまとめたら大混乱**になるで」

👩‍💻笑顔「なるほど！共通部分（date_vehicle→スケジュール）は同じ設計にして、違う部分だけ個別にしてるんですね！」

## 🔐 論理削除と制約 — データを守る仕組み

🐘「次は**安全装置**の話や」

👩‍💻「安全装置？」

🐘「このプロジェクトでは、データを**物理的に消さない**。`deleted_at` っちゅうカラムで**論理削除**しとる」

> 💡 **「論理削除」とは？**
> データを実際に削除せず、「削除された日時」を記録するだけの方式。
> 書類をシュレッダーにかけるのではなく、**「処分済み」のスタンプを押して倉庫に保管する**イメージです。

```
 物理削除 vs 論理削除

  【物理削除】🗑️ → 💨 消えた！もう戻せない！
  DELETE FROM users WHERE id = 5;

  【論理削除】📋 → 📦 倉庫に保管。いつでも復元可能！
  UPDATE users SET deleted_at = NOW() WHERE id = 5;
```

👩‍💻「なぜ論理削除にしてるんですか？」

🐘「**配車の履歴**が大事やからや。『3月に田中さんが何回ダンプ運転したか』とか、後から確認できなアカンやろ？」

👩‍💻笑顔「たしかに！削除しちゃったら履歴がなくなっちゃいますもんね」

🐘「ほんで、もう一つ大事なんが**ON DELETE CASCADE**や」

| 制約 | 意味 | 例 |
|---|---|---|
| `ON DELETE CASCADE` | 親を削除→子も自動削除 | 日付を消す→その日の配車も全部消える |
| `UNIQUE(email, deleted_at)` | 削除済みユーザーのメール再利用OK | 退職した田中さんのアドレスを新人が使える |
| `CHECK制約` | 値の組み合わせを制限 | user_id と driver_team_id は片方だけ |

👩‍💻感動「DBレベルでこんなに守ってるんだ…すごい」

## 🔗 中間テーブル — 多対多のつなぎ役

🐘「最後に**中間テーブル**の話や。これがまた初心者を惑わすやつでな」

👩‍💻疑問「中間テーブルって何ですか？」

🐘「例えばな。1人のドライバーが**複数の車両タイプ**を運転できる。逆に、1つの車両タイプを**複数のドライバー**が運転できる。この**多対多**の関係を管理するのが中間テーブルや」

```
 多対多の関係 = 合コンの席替え表 💑

  【ドライバー側】        【中間テーブル】       【車両タイプ側】
  ┌──────────┐    ┌──────────────────┐    ┌──────────────┐
  │ 田中さん  │───→│ user_vehicle_type│←───│ ダンプ       │
  │ 鈴木さん  │───→│                  │←───│ ジェットパック│
  │ 佐藤さん  │───→│  user_id    │    │←───│ WP・PKS      │
  └──────────┘    │  vehicle_   │    │    └──────────────┘
                   │  type_id    │    │
                   └──────────────────┘

  田中さん → ダンプ ✅、ジェットパック ✅
  鈴木さん → ダンプ ✅
  佐藤さん → ジェットパック ✅、WP・PKS ✅
```

🐘「このプロジェクトには中間テーブルが**2つ**ある👇」

| 中間テーブル | つなぐもの | 用途 |
|---|---|---|
| `user_vehicle_type` | ユーザー × 車両タイプ | 誰がどの車種を運転できるか |
| `notification_type_user` | ユーザー × 通知タイプ | 誰がどの通知を受け取るか |

👩‍💻笑顔「中間テーブルって、2つのテーブルの橋渡し役なんですね！」

🐘得意げ「そういうことや！さすガネーシャや！✨」
