バックエンドの裏側、全部見せたるわ！

ガネーシャ×ナツキの対話で学ぶ、このプロジェクトのLaravelバックエンド処理フロー

ブラウザからのリクエストは「ルーティング → ミドルウェア → コントローラー → (UseCase) → Model → Resource → ApiResponse」の順に流れ、それぞれが1つの仕事だけを担当する。この「責務分離」がバックエンド設計の核心や。

まず覚える3つ

バックエンドの全体像はこれでつかめる！

1
リクエストは「一方通行の流れ」 必須

ルーティング → ミドルウェア → Controller → UseCase → Model → Resource → ApiResponse。上流から下流へ、決まった順番で処理が進む。

2
各レイヤーには「やっていいこと」と「やったらアカンこと」がある 重要

Controllerはリクエストの受付係、UseCaseはビジネスロジック担当、Modelはデータベースへのアクセス担当。越権行為は禁止。

3
単純な処理はUseCaseを通さなくてもOK 効率化

単純なCRUD（データの取得・作成・更新・削除）ならControllerからModelを直接操作。複雑な処理だけUseCaseを経由する。

バックエンドって何をしてるの？

まずは全体のイメージをつかもう

ええか、ナツキ。バックエンドっちゅうのはな、レストランの厨房みたいなもんや。お客さん（ブラウザ）からは見えへんけど、注文を受けて料理を作って返す。その裏側の仕組みを全部見せたるわ！

レストランの厨房…？ でもレストランって、ホールスタッフとか料理長とか洗い場の人とか、色々いますよね。バックエンドにもそういう「役割分担」があるんですか？

そのとおりや！さすガネーシャの生徒やな！バックエンドにも6つの役割があるんや。まずは全体の流れを図で見てみぃ！

たとえ話：レストランの注文フロー

ブラウザからの通信をレストランに置き換えると、こうなります。

  • お客さん（ブラウザ） → 「カレーください」と注文
  • 入口の案内係（ルーティング） → 「カレーのご注文ですね、厨房へお通しします」
  • セキュリティ（ミドルウェア） → 「会員証を確認しますね…OK、入れます」
  • ホールスタッフ（Controller） → 「注文受けました！厨房にお伝えします」
  • 料理長（UseCase） → 「よし、この手順で作るぞ」
  • 冷蔵庫・食材庫（Model） → 「食材はここにあるよ」
  • 盛り付け係（Resource） → 「きれいにお皿に盛り付けました」
  • 配膳トレー（ApiResponse） → 「統一の形でお客さんにお届け」

リクエストの旅路：全体フロー

ブラウザからデータベースまで、データが通る道

1. ルーティング（routes/api.php）

URLを見て「どのControllerに渡すか」を決める案内係。

2. ミドルウェア（auth:sanctum等）

認証チェック（会員証の確認）やCORS対応を行うセキュリティゲート。

3. Controller + FormRequest

リクエストを受け取り、バリデーション（入力チェック）を実行。単純な処理ならここでModelを直接操作する。

4. UseCase（複雑な処理の場合のみ）

ビジネスロジックとトランザクション管理を担当する料理長。複数のModelを操作するときに登場。

5. Model（Eloquent ORM）

データベースとやり取りする倉庫番。テーブルとの対応関係やリレーション（テーブル同士のつながり）を管理。

6. Resource + ApiResponse

データを統一フォーマット（JSON）に整形して、ブラウザに返す盛り付け＋配膳係。

出てくる用語を先に知っておこう

これから何度も出てくる言葉たち

「ルーティング」とは？
URLを見て「どの処理を呼ぶか」を振り分ける道案内のこと。
カーナビの「目的地に合わせてルートを決める」と同じです。/api/vehicles というURLが来たら「車両のControllerに行ってね」と案内します。
「ミドルウェア」とは？
リクエストが本処理に届く前に実行されるセキュリティゲートのこと。
会社の入口のセキュリティチェックのように、「この人は入っていいのか？」を確認します。このプロジェクトでは auth:sanctum で認証を行っています。
「CRUD」とは？
データの基本操作4つの頭文字を取ったもの。Create（作成）、Read（読取）、Update（更新）、Delete（削除）。
ノートに書く・読む・書き直す・消す、と同じです。ほとんどの機能はこの4つの組み合わせでできています。
「トランザクション」とは？
複数のデータ操作を「全部成功」か「全部なかったこと」のどちらかにする仕組み。
銀行の振込と同じ。Aさんの口座から引いてBさんの口座に足す、この2つは絶対にセットで行われます。片方だけ成功してもう片方が失敗、なんてことがあると大変ですよね。

Step 1：ルーティング

URLを見て行き先を決める案内係

まず最初にリクエストが到着するのがroutes/api.phpや。ここに「このURLが来たら、このControllerに行ってね」っちゅう指示が全部書いてあるんや。

実際にはどんなルートが定義されてるんですか？

このコードがやること

routes/api.php に書かれたルート定義。/api/vehicles というURLにアクセスがあったら VehicleController の処理を呼ぶ、という指定です。

// ログイン（認証不要）
Route::post('/login', LoginController::class);
// 認証が必要なルート
Route::middleware('auth:sanctum')−>group(function () {
Route::apiResource('vehicles', VehicleController::class);
Route::apiResource('driver-teams', DriverTeamController::class);
});

post -- HTTPメソッドの指定。データを送信するときは POST、取得するときは GET を使う

auth:sanctum -- この中のルートは「ログイン済みの人しかアクセスできない」という認証ゲート

apiResource -- 1行で「一覧取得・詳細取得・作成・更新・削除」の5つのルートを自動生成するLaravelの便利機能

ちなみにな、このプロジェクトではURLはkebab-case（ハイフン区切り）っちゅうルールがあるんや。/api/driver-teams みたいにな！

apiResourceが自動生成する5つのルート

1行書くだけでこれだけ作られる

HTTPメソッド URL 処理 たとえ
GET /api/vehicles index（一覧取得） メニューを全部見る
POST /api/vehicles store（新規作成） 新しい料理を追加する
GET /api/vehicles/{id} show（詳細取得） 1品の詳しい情報を見る
PUT /api/vehicles/{id} update（更新） 料理の内容を変更する
DELETE /api/vehicles/{id} destroy（削除） メニューから外す

Step 2：ミドルウェア

セキュリティゲートを通り抜ける

ルーティングの次はミドルウェアや。ワシの教え子の徳川家康くんがな、「城に入る前には必ず門番が身分を確認せなアカン」って言うてたんや。ミドルウェアはまさにその門番やで。

…家康がそんなこと言ってたかは怪しいですけど、認証チェックの仕組みは理解できました。でも「Sanctum」って何ですか？

い、いや…家康くんはホンマに言うてたで！（汗）SanctumはLaravel公式の認証パッケージや。ログイン時にトークン（入場券）を発行して、以降のリクエストではそのトークンで本人確認するんやで。

たとえ話：映画のチケット（Sanctumトークン認証）

Sanctum認証は映画館のチケットに似ています。

  • ログイン → チケット売り場でチケット（トークン）を購入
  • APIアクセス → チケットを見せてスクリーンに入場
  • トークン期限切れ → チケットの有効期限が切れたので再購入
  • ログアウト → チケットを返却（無効化）

Step 3：Controller + FormRequest

注文を受け取るホールスタッフ

Controllerはな、レストランのホールスタッフや。お客さんの注文（リクエスト）を受け取って、内容をチェックして、厨房に伝える。でもな、ここで大事なルールがあるんや。

大事なルール？何ですか？

ホールスタッフが厨房に入って料理を作り始めたらアカンやろ？Controllerも同じで、複雑なビジネスロジックは書いたらアカンんや。自分の担当だけやる、これが大事なんやで！

Controllerがやること
  • リクエストの受け取り
  • 入力バリデーション（FormRequest経由）
  • 単純なCRUDならModelを直接操作
  • レスポンスの返却（Resource使用）
  • 複雑な処理はUseCaseに委任
Controllerがやったらアカンこと
  • 複雑なビジネスロジック
  • トランザクション管理（DB::transaction）
  • 複数Modelにまたがる操作

FormRequest：注文票のチェック係

入力データの検証は専用クラスに任せる

入力チェックはFormRequestっちゅう専用クラスに任せるんや。「名前は必須」「255文字以内」みたいなルールを定義しとくんやで。

このコードがやること

DriverTeamRequest クラス。「グループ名は必須で255文字以内」「説明は任意」というルールを定義しています。ルールに違反した入力が来たら、自動的に422エラーを返します。

class DriverTeamRequest extends FormRequest
{
public function rules(): array
{
return [
'name' => ['required', 'string', 'max:255'],
'description' => ['nullable', 'string'],
];
}
}

'required' -- 必須項目。空欄だったらエラーになる

'max:255' -- 最大255文字まで。それ以上はエラー

'nullable' -- 空欄でもOK。任意項目であることを示す

Controllerの2つのパターン

単純な処理と複雑な処理で道が分かれる

ここが一番大事なポイントや！Controllerには2つのパターンがあるんや。「単純な注文」と「特別な注文」で対応が変わるんやで！

Controller がリクエストを受け取る
処理は複雑か？
いいえ（単純なCRUD）
Controller → Model 直接操作

一覧取得、詳細取得、単純な作成・更新・削除

はい（複雑な処理）
Controller → UseCase → Model

複数Model操作、トランザクション、ビジネスルール検証

あ、なるほど！つまり全部の処理にUseCaseを挟む必要はないんですね。単純な処理はショートカットできるんだ！

そのとおりや！「カレー1つ」って注文やったら、ホールスタッフがそのまま盛り付けて出せるやろ？わざわざ料理長を呼ぶ必要はないんや。

Step 4：UseCase

複雑な注文を捌く料理長

UseCaseはな、「フルコースディナーを作る料理長」みたいなもんや。前菜→スープ→メイン→デザート、全部の段取りを考えて、食材（データ）の管理もするんやで。

具体的にどういうときにUseCaseを作るんですか？「この場合はUseCase」「この場合はController直」みたいな基準はあるんですか？

UseCase を作るべき5つの条件

1つでも当てはまったらUseCaseを作る

1
複数のModelを操作する

例：ダンプオーダー削除 + スケジュール削除を同時にやる

2
トランザクション管理が必要

例：「全部成功」か「全部なかったこと」にしたい操作

3
ビジネスルールの検証がある

例：過去の日付にはスケジュールを登録できない、重複チェック

4
外部サービスとの連携

例：S3にファイルをアップロードしてからDBに登録

5
複雑なクエリ条件がある

例：日付・車両・ステータス等、複数の条件を組み合わせた絞り込み

このプロジェクトにはUseCaseが80個もあるんやで！app/UseCases/{機能名}/ にドメインごとに整理されとるんや。さすガネーシャの設計や！✨

…自分で設計したみたいに言わないでください。でも80個って、多いですね。命名規則とかあるんですか？

あ、ああ…もちろんあるで！「{動詞}{Model名}UseCase」っちゅう命名ルールや。例えば StoreDumpOrderUseCase（ダンプオーダーを保存する）みたいにな。

Step 5：Model（Eloquent ORM）

データベースとやり取りする倉庫番

Modelはデータベースのテーブルと1対1で対応するクラスや。「Vehicle（車両）」というModelがあったら、データベースに「vehicles」というテーブルがあるんや。

ModelにはPascalCase・単数形、テーブルはsnake_case・複数形って聞きましたけど、それ以外にModelが持つ機能って何ですか？

fillable定義

どのカラムに値を入れていいかを定義。勝手にデータを書き換えられないよう守る「許可リスト」。

リレーション

テーブル同士のつながりを定義。「この車両はどのチームに属するか」のような関係性。

クエリスコープ

よく使う検索条件をメソッド化。「ダンプ車だけ取得」のような絞り込みを再利用可能にする。

Step 6：Resource + ApiResponse

盛り付け＋配膳で統一フォーマットに

最後の仕上げや！Resourceクラスが「どのデータをどういう形でブラウザに返すか」を決めて、ApiResponseが統一フォーマットに包んで返すんや。

統一フォーマットってどんな形ですか？

成功時のレスポンス
{
"success": true,
"message": "成功しました",
"data": { ... }
}
エラー時のレスポンス
{
"success": false,
"message": "エラーメッセージ",
"request_id": "req_67890..."
}

番外編：エラーが起きたらどうなる？

ApiExceptionHandlerが全部まとめて面倒を見る

ここがこのプロジェクトの賢いとこやで。エラーが起きたらApiExceptionHandlerが全部キャッチして、種類ごとに適切なレスポンスを返すんや。各Controllerで個別にエラー処理する必要がないんやで！

すごい…！それって、エラー処理を1箇所にまとめてるってことですよね。めちゃくちゃ効率的じゃないですか！

401 認証エラー

ログインしてない人がアクセスしようとした。「会員証がありません」

403 権限エラー

ログインはしてるけど権限が足りない。「この部屋は立入禁止です」

404 未検出エラー

指定したデータが見つからない。「その棚には何もありませんでした」

422 バリデーションエラー

入力内容がルールに違反。「名前が空欄です」などフィールド別にエラーを返す

500 サーバーエラー

予期しないエラー。request_id を生成してSentry（エラー監視サービス）に自動送信。本番環境ではエラー詳細を隠し、request_id だけを返す。開発者はこのIDでエラーを追跡できる。
